# Claude Codeの最新プラクティスに関する会話まとめ

整理日：2026-10-03

本書は、Claude Codeの活用について交わした会話の目的・前提・論点・提案をまとめたものである。運用ルールの適用やプラグインの導入を完了した記録ではない。ユーザーの要望と、アシスタントの提案を区別する。

## 1. 会話の出発点

最初の要望は、このリポジトリの開発を、Anthropic公式に基づく最新のClaude Code（以下、CC）のプラクティスで進めたい、というものだった。

その後、「もっと調べて」「古い情報が混ざっていないか」という確認が入った。一般的な開発のベストプラクティスや昔からある定番を紹介するだけでは不十分であり、公式の根拠と情報の鮮度が重要である。

求めているのは、単なる実装手順ではなく、現在のCCの機能を踏まえて、このリポジトリでの開発の進め方をどう更新するか、という説明である。

## 2. GitHub Issueへのタスク化は済んでいる

開発内容は、すでにGitHub Issueへタスク化されている。「何を作るか」の分解を最初からやり直すことが目的ではない。

対象には、TypeScript・pnpmの構成、Coreの契約と依存境界、安全なログ、Playwright Adapter、手動認証、AWS連携、Use Case、Composition Root、CLI、CI、E2Eなどがある。

知りたいのは、これらの既存Issueを、最新のCCを活用してどう進めるのがよいか、ということである。

追加の管理フレームワークを作るより、実際の実装タスクを通じてCCの機能を試す方向を提案した。

## 3. 個人開発と最新CCのキャッチアップを両立したい

ユーザーは、個人開発を進めながら、最新CCのプラクティスをキャッチアップすることが目的だと明示した。

- 開発そのものを進める。
- 同時に、最近のCCで何が変わったかを実践的に理解する。
- チーム向けの重い運用や、学習のためだけの設定を増やしすぎない。

この前提から、実際のIssueで機能を使い、効果を確認して役立つものを残す、という進め方を提案した。「最新だから全部使う」という方針ではない。

## 4. Auto／Planの基本説明は不要

ユーザーから「最近はPlanモードをあまり使わないのでは？」という問いがあった。その後、半年前のプラクティスとAuto／Planの有用性はすでに知っている、と明示された。

したがって、Auto／Planの利点を説明し直したり、「まずPlanで計画してから実装する」という一般論を繰り返したりすることは、今回の目的に合わない。

答えるべきなのは、既知の基本を前提に、直近のCCの変化によって開発の進め方をどう更新するべきか、という点である。

なお、会話では「Planが廃れた」「今後は使わない」という結論を確定していない。最近の利用傾向についても、根拠なしに断定しない。

## 5. 現在の内蔵機能と従来のプラグインを区別する

最新プラクティスを考える際は、現在のCCに備わっている機能と、外部プラグインで追加する機能を区別する。

検討対象として、検証・レビューを支える `/verify`、`/code-review`、指示内容を点検する `/doctor prompt-audit` などが挙がった。

昔の紹介記事で定番だったプラグインを、そのまま現在の推奨構成として採用しない。現在の内蔵機能で目的を満たせるかを先に確認する。

これらは一括導入・常時使用を決めたものではない。利用時には、現行の公式資料とインストール済みCCでの提供状況を確認し、Issueに必要なものから試す。

## 6. コーディングルール用Skillsは必要か

追加の問いは、このリポジトリのコーディングルールをSkillsとして持つ必要があるか、必要ならプラグインを導入するべきか、というものだった。ここでも、最新プラクティスに沿うことが条件である。

アシスタントの提案は、コーディングルール自体は必要だが、今の段階では汎用的な規約Skillsプラグインを入れる必要性は低い、というものだった。

このリポジトリでは、一般的な「きれいなコード」の規約より、[設計・要求ドキュメント](<MoneyForward Automation 設計・要求ドキュメント.md>)にある依存境界と安全性を守ることが重要である。

### 6.1 指示・知識・自動検証の役割分担

| 仕組み | 提案した役割 |
|---|---|
| `CLAUDE.md` | 設計書への入口、共通方針、利用可能になった検証コマンドを短く記載する |
| `.claude/rules/` | Core・Playwright・認証／ログなど、対象別の短い制約を記載する |
| 型チェック・lint・境界テスト | 機械的に判定できる重要な制約を保証する |
| Skills | 詳しい設計パターン、参照資料、繰り返す作業が増えたら追加する |

Skillsで規約・パターン・スタイルガイドを扱うこと自体は、公式に認められた用途である。「規約をSkillsに置くのは古い／間違い」という判断ではない。

現行Skillsには対象パスを限定する仕組みもあるため、Rulesだけがパス別に使える、という区別でもない。今回は短い制約が中心なのでRulesから始め、詳しい知識や再利用する手順が増えたらSkill化する、という提案である。

### 6.2 このリポジトリで優先するルール

| 対象 | 明示する制約の例 |
|---|---|
| Core | Playwright・AWS・実行環境に依存しない。Portは外部の能力単位とし、過剰な抽象化を避ける |
| Playwright Adapter | `Page`・`Locator`を外に漏らさない。クリックできただけで成功と判定しない |
| 認証・ログ | Secret・Cookie・金融情報をログに出さない。認証チャレンジを自動回避しない |

指示ファイルはClaudeの判断を支援するものであり、強制的な保証ではない。依存境界などを型・lint・境界テストで検証する提案は、この違いに基づく。

### 6.3 プラグインを検討するなら

規約集ではなく、開発能力やレビューを補うAnthropic製プラグインを候補として挙げた。

- `typescript-lsp`：TypeScript／JavaScriptの定義ジャンプ、参照検索、エラー検出を補う。TypeScript実装開始時の候補。言語サーバーは別途必要。
- `security-guidance`：編集・変更差分へのセキュリティレビューを補う。認証・金融情報処理と相性がよい。リポジトリ固有の脅威や注意点は `.claude/claude-security-guidance.md` に記載できる。

`security-guidance` のモデルレビューには追加のモデル使用量が発生する。また、変更やコミットを強制的に止めるゲートではなく、補助レビューである。

これらは候補であり、会話の中ではインストールしていない。

## 7. Dynamic Workflowsは対象外

ユーザーは、Dynamic Workflowsは不要と明示した。

最新プラクティスを追うことと、Dynamic Workflowsを導入することは別である。今後の提案も、通常のCCセッション、リポジトリの指示、自動検証、必要なプラグインで成立する範囲に絞る。

## 8. 現時点の提案と未確定事項

通常の開発の進め方としては、既存Issueを選び、CCで調査・実装・検証を行い、差分レビューを経てコミット／PRへ進む流れを提案した。人間が押さえるのは、目的・守る制約・完了条件である。

設定については、短い `CLAUDE.md`、対象別Rules、型・lint・境界テストを土台にし、実装開始時にLSP、認証処理では必要に応じてセキュリティレビューを試す構成を提案した。

一方、次の事項は未確定である。

- 具体的なRulesの内容と配置。
- 導入するプラグインと導入時期。
- 各Issueで使うCCの機能と、採用判断の結果。
- 直近の変更を踏まえた、Auto／Planを含む具体的な運用の更新点。

会話全体の中心は、「Skillsを入れるか」だけではない。半年前の基本を知っている個人開発者が、既存Issueを進めながら、Anthropic公式の最新CCの使い方へどう更新するか、という問いである。

コーディングルールとプラグインは、その目的を支える一部分として扱う。
