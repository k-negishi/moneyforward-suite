# 0028. モバイル Suica を対象から外し、初期 Job を金融機関のデータ一括更新に限定する

- Status: Accepted
- Date: 2026-10-03

## Context

ADR-0027 では、初期 Job `refresh-accounts` を「金融機関のデータ一括更新 → モバイル Suica の更新」の 2 段階とする決定をしていた。その後、マネーフォワード ME がモバイル Suica（JRE ID）の自動取得に対応したため、手動更新の自動化が不要になった。このため Suica を対象から完全に外し、初期 Job のスコープを金融機関のデータ一括更新のみに限定する。

ADR-0027 の Suica 以外の決定（Job 名 `refresh-accounts`、認証要求（セッション失効）時の停止、一括更新の部分失敗時の扱い）は維持する。

本 ADR は ADR-0027 を置き換える（Supersedes: ADR-0027）。

## Decision

初期 Job `refresh-accounts` のスコープを金融機関のデータ一括更新のみとする。モバイル Suica の更新は実装しない。

実機の一括更新は各金融機関の行ごとに更新されるため、受付・結果確認は行の変化を基準に行う（ADR-0020 の状態変化による成功判定を一括更新に適用する）。

認証要求（セッション失効）を検知した場合は処理を停止する（ADR-0011・ADR-0012・ADR-0015）。一括更新が部分的に失敗した場合（一部の金融機関のみ失敗）は、結果を合成して部分成功として表現する。

## Consequences

- 初期 Job のスコープが単一の処理になり、2 段階の実行順序・結果合成が不要になる。部分成功（一部の金融機関のみ失敗）の表現は残る。
- Job 名 `refresh-accounts` と Use Case 名 `RefreshAccountsUseCase` は維持する（改名しない）。
- 受付・結果確認を行の変化で行うため、どの行がどう変化したかを Adapter から取得できるようにする必要がある（フォローアップ）。
- ADR-0027 の Suica に関する記述（2 段階の実行順序、Suica 更新の続行など）は履歴であり、実装の基準にはならない。
- ADR-0008・ADR-0009 の例示は決定時点の記録として残る（書き換えない）。

## Alternatives considered

- Suica を当面保留する（実装はしないがスコープに残す）: マネーフォワード ME の自動取得成功により Suica の更新自体が不要になったため、スコープに残すと不要な実装・検証の対象が残り続ける。完全廃止として明確にするため却下。
- Suica を別 job に残す: 将来必要になった場合に備える案。現時点で必要とする根拠がなく、実行されない job を Job Router の Allow List に残すのは不要な複雑さになるため却下（必要になった時点で新しい job として設計する）。
