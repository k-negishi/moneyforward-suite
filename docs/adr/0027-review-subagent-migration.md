# 0027. レビュー工程をリポジトリ専用サブエージェント 2 体へ移行する

- Status: Proposed
- Date: 2026-10-03

## Context

これまでレビューは、Claude Code 内蔵の `/code-review` Skill を起動する運用だった。しかし内蔵 Skill は既定の effort（medium）で 8 個のファインダー角度と候補ごとの検証エージェントを起動する設計で、エージェント起動数が多く、この規模の開発に対して過剰である。

一方、本リポジトリ固有のレビュー基準（Core のランタイム非依存、Port の粒度、Playwright の成功判定、Secret とログ、認証チャレンジの扱い）は、既に `.claude/rules/` に 3 ファイルとして存在する。内蔵 Skill はこれらの基準を判断材料として持たず、汎用的な観点でレビューする。

Anthropic 公式ドキュメントは、カスタムサブエージェントをレビューの正規の手段として認めている（`code-reviewer` は代表例）。あわせて、diff と与えた基準だけを見る新鮮なコンテキストのレビュアーを推奨し、`tools` から `Agent` を外すことでサブエージェント起動を構造的に禁止できるとしている。

## Decision

レビュー工程を、リポジトリ専用のサブエージェント 2 体（`code-reviewer` / `security-reviewer`）で行う。内蔵 `/code-review` は使わない。

1. **2 体に分ける**。`code-reviewer` は ADR との整合、Core / Adapter の依存境界、Playwright の成功判定、回帰リスクを主担当とする。`security-reviewer` は Secret・Cookie・storageState・金融明細の混入防止、allow-list ログ、認証チャレンジの非回避、fail closed を主担当とし、あわせて汎用脆弱性クラスも担当する。判断の構えが異なるため分離する。
2. **権限で禁止する**。両者とも `tools` は `Read` / `Grep` / `Glob` のみとし、`Agent` と `Bash` を含めない。サブエージェント起動と実サービスへの接触を、プロンプトではなくツール権限として不可能にする。
3. **基準は `.claude/rules/` に一本化する**。エージェントは基準を再定義せず、変更ファイルを Read することでパススコープのルールを読み込む。基準の二重管理を避ける。
4. **recall を優先する**。担当外でも確信のある問題は報告し、重複は許容する。指摘には `CONFIRMED` / `PLAUSIBLE` の確度を付け、`REFUTED` のみ除外する。採否はメインエージェントが判断する。
5. `security-guidance` プラグインの扱いと `.claude/claude-security-guidance.md` の新設可否は、本 ADR の対象外とし別途判断する。

## Consequences

- エージェント起動数が最大 2 に固定され、内蔵 Skill の 8 ファインダーと検証の連鎖に対して大幅に減る。
- レビュー基準が `.claude/rules/` と ADR に一元化され、基準を変えてもエージェント定義を直す必要がない。
- 権限制限により、レビュアーがコードを書き換えたり実サービスに触れたりする経路が無くなる。
- 内蔵 Skill が持つ多角的な観点（言語別の落とし穴、削除された振る舞いの追跡、呼び出し元の横断確認など）は失われる。重要な変更では観点不足が起き得る。
- パススコープのルールがサブエージェントのコンテキストで自動発火するかは公式に明記が無く、未確認である。両エージェントには、自動読み込みされていない場合にルールと ADR を直接 Read するフォールバックを入れて緩和している。
- 2 体は独立して起動できるため、片方だけを実行すると守備範囲に穴ができる。CLAUDE.md で両方の起動を開発フローの手順として定める。

## Alternatives considered

- **内蔵 `/code-review` の effort を下げて使い続ける**: `low` を記憶させればサブエージェントは使われないが、`low` はテスト・fixture の hunk をスキップし full-file read も行わないため、金融関連のレビューとしては浅い。また本リポジトリ固有の基準を判断材料に持たない。却下。
- **1 体の統合レビュアーにする**: エージェント起動数は 1 で済むが、アーキテクチャの指摘とセキュリティの指摘が同じ重みで混ざり、セキュリティ観点が埋もれる。金融データを扱う以上、セキュリティレビューは独立して必ず走る必要がある。却下。
- **`security-reviewer` を汎用脆弱性クラスに限り、リポジトリ固有の不変条件は `security-guidance` に任せる**: 同プラグインがこの環境で動作しているかが未検証であり、動作未確認の層に守備範囲を空けるのは漏れに直結する。却下。
- **2 体の担当を排他的に分け、重複を排除する**: 境界の判断に迷った指摘が落ち、漏れが増える。重複を許容コストとして受け入れ、recall を優先する。却下。
- **`.claude/claude-security-guidance.md` を新設し、セキュリティ基準をそちらにも書く**: 基準が `.claude/rules/auth-and-logging.md` と二重管理になり、改版時に食い違う。却下。
- **カスタムエージェントを追加せず、汎用サブエージェントへの独自プロンプトで代替する**: 呼び出しごとにプロンプトを書き直すことになり、権限制限も効かない。却下。
