# 0030. 企画段階の文書を proposals に置き、決着時に ADR へ蒸留する

- Status: Accepted
- Date: 2026-10-03

## Context

文書は役割で分けている（ADR-0001）。決定は ADR（不変）、要件は要件文書（生きている）、現在の構造はアーキテクチャ文書（生きている）。しかし決定前の探索の置き場が定まっていない。

現在、企画段階の検討は GitHub Issue と会話に依存している。Issue はタスクチケット（完了条件・依存関係・Epic の子 Issue）として確立しており、未決定の企画を混ぜると「やること」の一覧が濁る。検討の成果物（構想・スコープ案・調査の知見・未解決の問い）も Issue コメントに埋もれ、決定に至る経緯を辿りにくい。

先行事例には次がある。RFC と ADR の分離（「RFC は探索、ADR は決定」）は広く使われるが、レビュー期間・承認・合意形成を伴うフル RFC プロセスは、決定の仕組みを持たず議論が終わらないとして軽い組織では維持が難しい（Tor Project は RFC を廃止して ADR へ移行した）。Kubernetes KEP は provisional → implementable → implemented の状態機械で「どこまで決まったか」を示し、rejected も履歴として残す。Shape Up の pitch は Problem / Appetite / Solution / Rabbit holes / No-gos の 5 要素で、やらないことと罠を先に書いて探索の境界を決める。

## Decision

企画段階（決定前）の文書の置き場と運用を次のとおり定める。

1. 置き場は `docs/proposals/` とし、1 企画 1 ファイルで書く。書式は同ディレクトリの `template.md`（Shape Up の pitch の圧縮版）に従う。
2. 文書は `Exploring` / `Concluded` / `Dropped` の状態を持つ（KEP の状態機械の簡略版）。
3. 決着（Concluded）したら、決定は ADR に、要件の変化は要件文書に書く。proposals の文書は削除する（経緯は git 履歴に残る）。ADR を決定の契約、proposals を交渉の記録として扱う。
4. 却下（Dropped）も理由を文書に残してから削除する。将来蒸し返され得る却下は ADR の Alternatives considered にも書く。
5. proposals を使うのは、複数の決定に分かれる・調査を伴う・複数セッションにまたがる企画に限る。単発の決定は会話で詰めて ADR だけを書き、ADR の Context が経緯を兼ねる。
6. フル RFC プロセスは導入しない。Issue は実装タスク専用のままとする。

## Consequences

- 決定前の探索がリポジトリ内に残り、将来の読者（人間・AI エージェント）が決定の前提を辿れる。Issue コメントに埋もれない。
- Issue は決定後の実行単位に純化される。
- 決着時に ADR を書く運用は既存のままで、新しい負担は増えない。一方、探索の生の経緯（議論の揺れ）は git 履歴を辿る必要がある。
- 生きている文書が 1 種類増えるが、決着で消えるため陳腐化した文書は滞留しない。
- 機械的な強制はなく、使うかどうかの判断はエージェントと人間に依存する。

## Alternatives considered

- Issue を企画にも使う: タスクチケットとして確立しており、未決定の企画を混ぜると状態管理が濁るため却下。
- フル RFC プロセスを導入する: レビュー期間・承認・合意形成の手続きは個人開発では維持できず、決定に至らない議論が残るため却下。
- ADR の Proposed を探索に使う: ADR は決定済みを前提とする書式であり、流動的な探索を書くと Proposed が滞留して索引が読みにくくなるため却下。結論が固まった起案は従来どおり Proposed の ADR で行う。
- 要件文書の「将来構想」に書く: 要件と探索が混在し、ADR-0001 が解消した役割の混在に戻るため却下。
- 決着後も proposals を残す: 蒸留先（ADR・要件文書・git 履歴）があり、残すと二重管理になるため却下。
