# 0026. ADR の作成トリガーを定め、開発フローに組み込む

- Status: Accepted
- Date: 2026-10-03

## Context

ADR 基盤（[0001](0001-adopt-adr.md)）を導入した次の課題は、ADR を「いつ・どう作るか」を仕組みにすることである。決定は 3 つの経路で生まれるため、経路ごとに ADR 化のタイミングが定まっていないと、記録の漏れと、些細な決定まで記録するノイズの両方が起きる。

- 初手プラン: 実装前の計画で設計判断が固まる。
- 直接実装: 実装中のやり取りで決定が生まれる。
- Issue: Issue の議論で設計が決まる。

日本語の実践記事（軽量 ADR・可逆/不可逆の重み付け・「ADR の最初の読者は AI エージェントになった」）を踏まえ、重い決定だけを厚く記録し、why を将来の読み手（人間と AI エージェントの両方）に残す方針を採る。

本 ADR の採番は 0026 とする。ADR-0002〜0025 は並行実施中の #21（旧設計書からの遡及記録）が作成するため、現時点では空きである。欠番は再利用しない規約のため、0002〜0025 の空きは一時的なものとし、本 ADR は 0026 を使う。

## Decision

ADR の作成トリガーと運用方法を次のとおり定め、開発フローに組み込む。

1. **トリガー基準**: 次のいずれかに当てはまる決定を ADR にする。後戻りが難しい／複数の選択肢と選定理由がある／リポジトリ横断の制約になる／セキュリティ・認証・金融データに関わる／既存 ADR を置き換える。判断に迷ったら「6 ヶ月後に『なぜ？』と聞かれるか」を補助線にする。可逆で局所的な決定は書かない（重い決定だけ厚く記録する）。
2. **3 経路**: 初手プランはプラン承認時に ADR 化する。直接実装は完了報告の前に確認し、対象なら同一 PR に同梱する。Issue で決めた設計は ADR 化して相互リンクする（Issue は決定の置き場にしない）。既存 ADR と矛盾する変更は、進める前に新 ADR（supersede）を提案する。
3. **仕組み**: `adr` スキル（判定基準・採番・テンプレート準拠・索引更新・supersede の手順）と CLAUDE.md の短い起動条件で運用する。Hook は使わない（決定の有無は機械判定できないため）。

品質は次の 4 点を基準とする。分量は「PR description の延長」として 1 画面。Alternatives considered は最重要欄とし、検討した代替案と却下理由を書く。将来の AI エージェントが最初の読者になる前提で why を省かない。原典・会話に無いことを推測で書かない。

## Consequences

- 経路ごとに ADR 化のタイミングが定まり、決定の記録漏れが減る。
- 判定基準により可逆で局所的な決定は対象外となり、記録は重い決定に集中する。
- 起動条件（CLAUDE.md）と手順（スキル）が分かれるため、片方だけ更新すると食い違う可能性がある。食い違い時は ADR 置き場の README を正とする。
- 機械的な強制は無く、基準の適用はエージェントと人間の判断に依存する（漏れを完全には防げない）。

## Alternatives considered

- スキルのみで運用する（CLAUDE.md に起動条件を書かない）: スキルは会話の文脈で参照されるため、起動条件が無いと発火が漏れる。CLAUDE.md の短い起動条件を併用する形にした。
- CLAUDE.md のみで運用する（スキルを作らない）: 判定基準・採番・索引更新・supersede の手順まで CLAUDE.md に書くと肥大し、開発ワークフローの記述に手順が散らばる。詳細はスキルに集約した。
- Hook で強制する: 決定の有無は機械判定できず、誤検知（些細な変更での発火）と見逃し（判断を伴う変更）の両方が起きるため却下。
- 判定基準を広げ、すべての設計判断を ADR にする: 記録がノイズで埋まり、重い決定が埋もれるため却下。
- 判定基準を絞り、不可逆な決定のみに限る: 複数の選択肢と選定理由がある決定や、リポジトリ横断の制約の記録が漏れるため却下。
