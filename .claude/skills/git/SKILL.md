# Git 規約と基本手順

このリポジトリでブランチ操作・コミット・PR 作成を行うときの規約と手順。既存の履歴の形式と揃えることで、後から履歴を追う人とレビューする人が経緯を把握しやすくなる。

## ブランチ命名

機能開発ブランチは `feature/<slug>` の形式にする。履歴を見たときに種別と内容がすぐ分かる状態を保つため。

- `feat/` は使わない（`feature/` に統一する）。Issue 番号は付けない。
- `<slug>` は内容を表す英小文字の kebab-case。例: `feature/monorepo-foundation`
- chore・fix など他種別のブランチは、種別プレフィックスを付ける（例: `chore/plan-review-workflow`）。

## コミットメッセージ

- 日本語で書く（中国語・韓国語は使わない）。
- 何を変更したかだけでなく、**変更の目的や理由**が伝わるように、省略せず具体的に記述する。後から履歴を読む人が「なぜこの変更が必要だったか」を追えるようにするため。
- 1行目に要約を書き、本文に目的・理由・影響を書く。
  - 1行目の例: `fix: pnpm のバージョン強制を engineStrict に切り替える（#2）`

## 基本手順（検証 → コミット → PR）

1. **検証**: コミット前に、変更に対応する検証を実行する。利用可能なコマンドは CLAUDE.md と各 `package.json` の scripts から確認する（このスキルには列挙しない。陳腐化を避けるため）。実行できない検証は理由を報告する。
2. **コミット前確認**: `git status` と `git diff` で、無関係な既存変更が混ざっていないことを確認する。無関係な変更はコミットに含めない。
3. **コミット**: 上記のメッセージ規約に従って作成する。
4. **PR**: `gh pr create` で作成する（ベースは `master`）。本文に変更内容・目的・検証結果を記載する。

## マージ方法

PR のマージは**通常マージ（マージコミット）**を使う。`gh pr merge <番号> --merge` を使い、`--squash` は使わない。個別コミットの記録を履歴に残し、squash で潰さないため。

- リポジトリ設定で squash merge は無効化済み（`allow_squash_merge=false`）。`--squash` は失敗し、GitHub UI にも選択肢が出ない。
- master は保護されており PR 経由でのみ反映する（管理者も迂回不可）。

## 並行作業の注意

このリポジトリでは、同一リポジトリを複数のセッションや worktree が同時に使うことがある。git 操作の直前に `git status` と `git log` を確認し、他セッションの変更を上書きしたり、自分のコミットへ混入させたりしない。

隔離して作業したい場合は worktree を使う: `git worktree add ../<name> -b <branch> origin/master`

## 安全則

コミット・push・PR 作成・デプロイは、ユーザーから依頼された範囲でのみ行う（CLAUDE.md「安全性と実行範囲」の原則に従う）。
