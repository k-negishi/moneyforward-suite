# ADR（設計判断の記録）の規約と手順

このリポジトリで設計判断を ADR として記録するときの判定基準と手順。ADR の最初の読者は将来の AI エージェントになることを前提に、結論だけでなく「なぜそう決めたか」「何を却下したか」を残す。運用規約の原文は ADR 置き場の README にあり、このスキルと食い違う場合は README を正とする（二重管理を避けるため、規約の全文はここに写さない）。

## ADR 置き場の探索

標準の置き場は `docs/adr/` とする。作業の前に、この場所に README（運用規約・決定一覧）と template（書式）があるかを確認する。

- 見つかった場合: その README の規約に従う。このスキルと食い違う場合は README を優先し、食い違いをユーザーへ報告する。
- 見つからない場合: 勝手に新しい置き場を作らず、ユーザーに置き場を確認する。

## ADR 化すべきかの判定基準

次のいずれかに当てはまる決定は ADR にする。「6 ヶ月後に『なぜ？』と聞かれるか」を判断の補助とする。

- 後戻りが難しい（不可逆、または変更コストが大きい）
- 複数の選択肢を比較し、選定理由がある
- リポジトリ横断の制約になる
- セキュリティ・認証・金融データの扱いに関わる
- 既存の ADR を置き換える

可逆で局所的な決定（例: 変数名、小さな実装の詳細）は ADR にしない。記録がノイズで埋まると、重い決定が埋もれるため。

### 確認するタイミング

- 初手プラン: プラン承認時に、プラン内の設計判断が対象かを確認し、対象なら ADR 作成をプランに含める。
- 直接実装: 完了報告の前に確認し、対象なら同一 PR に ADR を同梱する。
- Issue: Issue で設計を決めた場合は ADR 化して相互リンクする。Issue は決定の置き場にしない。

既存の ADR と矛盾する変更は、進める前に新 ADR（supersede）を提案し、ユーザーの承認を得る。

## 作成手順

1. **採番**: ADR 置き場のファイルを走査し、既存の最大番号 +1 を新しい番号にする。番号は不変であり、欠番を再利用しない。
2. **ファイル作成**: `NNNN-slug.md`（4 桁ゼロ埋めの連番、slug は内容を表す英小文字の kebab-case）を作成し、書式は template に従う（Status / Date / Context / Decision / Consequences / Alternatives considered）。
3. **起案**: Status は `Proposed` で起案する。独断で `Accepted` にせず、ユーザーの承認を得てから `Accepted` にする。
4. **索引更新**: 決定一覧の表に新しい ADR の行を番号順で追加する。

## 置き換え（supersede）手順

承認後の ADR は書き換えない。決定を変えるときは次の手順をとる。

1. 新しい ADR を作成し、Context に旧 ADR を置き換える理由を書く。
2. 旧 ADR は Status 行のみ `Superseded by ADR-NNNN` に変更する。本文は履歴として凍結し、書き換えない。
3. 決定一覧の Status も更新する。

## 品質基準

- 分量は「PR description の延長」として 1 画面程度に収める。長い設計文書にしない。
- Alternatives considered は最重要の欄である。検討した代替案と、採用しなかった理由を書く。
- 将来の AI エージェントが最初の読者になる前提で、why（なぜ決めたか）を省かない。
- 原典・会話に無いことを推測で書かない。記録が無い場合はその旨を書く。
